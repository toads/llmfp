# Evidence model

`llmfp` currently answers a narrow question: **which network infrastructure
performed an observed web-tool callback?** It does not authenticate the model
that generated an API response.

## What happens during a test

1. The local CLI registers a fresh Interactsh session and creates a random host
   and path under the selected probe server.
2. The CLI sends that exact URL to the API endpoint selected by the user and
   requests a hosted web-search or web-fetch operation.
3. The probe service records DNS and HTTP activity associated with the unique
   URL. `llmfp` decrypts the session events locally.
4. For an HTTP callback, `llmfp` parses the remote address, path, and User-Agent.
5. It downloads the provider-published network registries, records their hashes
   and retrieval times, and compares the callback address with their CIDRs.

The API key is sent only to `--base-url`. The probe URL appears in the prompt.
The probe operator can observe callback metadata, and registry hosts can observe
ordinary downloads from the machine running the CLI.

## How to interpret the evidence

| Observation | Supported conclusion | Unsupported conclusion |
|---|---|---|
| Exact HTTP path and official CIDR match | The callback associated with this test arrived from an address in that published tool/bot registry | The claimed generation model is genuine |
| User-Agent match without CIDR match | A header resembled a provider's documented client | The callback came from that provider; headers are forgeable |
| HTTP callback without a registry match | Some infrastructure fetched the unique URL | Which provider or model was responsible |
| DNS callback only | Some participant resolved the unique hostname | That an HTTP fetch or hosted tool completed |
| No callback | Nothing reached the collector before timeout | That the relay is fake or that no tool was attempted |
| Model name echoed by the API | The endpoint returned that string | That the endpoint actually ran that model |

`ExactPathFetched` correlates an event with the test, but it is not a secret
challenge: the API endpoint sees the path and can fetch it directly. Likewise,
a relay can invoke a genuine third-party tool independently of the model used
for generation. For these reasons, even a strong tool-layer result remains
separate from model identity.

## Threat and trust boundaries

- A malicious relay controls its response body, reported model name, headers,
  timing, and whether it follows the probe URL.
- The probe service controls the event records returned to the client. Use a
  reviewed self-hosted Interactsh deployment when that trust is unacceptable.
- Provider registries can change. Reports retain the registry URL, fetch time,
  and SHA-256 so the evidence can be reviewed later.
- NAT, proxies, egress gateways, and provider routing can cause the observed IP
  to identify a serving stack rather than an organization that generated text.
- Behavioral fingerprints are probabilistic and can drift with model updates,
  system prompts, sampling parameters, safety layers, and serving providers.

## Reporting language

Prefer: "The web callback was observed from an IP in provider X's published
tool registry."

Avoid: "This proves the response was generated by model X."

Future behavioral methods will be reported as an independent evidence layer.
They will not silently upgrade a tool-layer match into model authentication.
